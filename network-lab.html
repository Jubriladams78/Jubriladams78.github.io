Network Troubleshooting Lab

WGU D412, Network Analytics and Troubleshooting. I worked six help desk tickets in a simulated enterprise network and passed all six with a 100% score in November 2026.

This is a graded assessment that other students still take, so this page shares my methods and tools, not the ticket answers. The same applies to my GitHub repository.

The environment

The lab ran in GNS3 and modeled a small company network.

Routers

Several VyOS routers connecting user, admin, server, and DMZ subnets.

Firewall

OPNsense, separating the LAN, the DMZ, and the internet.

Servers

Windows Server 2016 for DNS, Ubuntu Server, and Linux and Windows servers in a DMZ.

Clients

A Windows 10 laptop, a Linux desktop, and a test PC.

Tools

Wireshark, PuTTY, TightVNC, the OPNsense web console, and the Linux and Windows command line.

How I worked each ticket

  1. Ask the requester first. What changed, when it started, what still works, and whether I may connect to their machine. Two requesters said no, so I proved where the fault lived from the network side before asking again.
  2. Test the path one hop at a time. Local IP and gateway, then the gateway, then the next router, then DNS. I changed nothing until a test pointed at one device.
  3. Compare against a known good answer. For DNS, I compared the internal server's reply with a public resolver. For routing, I compared each router's table with the network map.
  4. Make the smallest fix that solves it, then save the change so it survives a reboot.
  5. Verify from the user's side, explain the cause and the fix in plain language, and ask the requester to confirm.

The six kinds of problem

Ticket 1: Identifying a suspicious server from a packet capture

  • Wireshark
  • Packet capture

The situation. A security analyst reported an illegal service on the network and had only a capture file to go on.

My method. Filter the capture down to the protocol in question, read what the server says about itself, and name the host from that evidence. Save the result where the requester asked and leave the server running until told otherwise.

Ticket 2: Users sent to the wrong website

  • nslookup
  • Windows Server DNS
  • Ubuntu

The situation. One website opened a different page while every other site worked, which pointed to name resolution.

My method. Ask the internal DNS server and a public resolver the same question and compare the answers. Where they differ, inspect the internal server's configuration, fix the cause at the source, and repeat the same lookup to prove it.

Ticket 3: Servers that cannot reach other networks

  • ping
  • tracepath
  • VyOS
  • GNS3

The situation. A server could not reach other networks or the internet, which blocked updates.

My method. Test one hop at a time: local settings, the gateway, the next router, then DNS. Read the replies to tell a loop from a dead end, follow the traffic upstream, make the smallest router change that fixes it, and save the change so it survives a reboot.

Ticket 4: A device that dropped off its network

  • VyOS router
  • Switch configuration
  • Windows

The situation. A company laptop lost network access over its ethernet cable.

My method. Confirm the router and switch are healthy before touching the client. Then compare the client's adapter settings with the network design, and change only what does not match.

Ticket 5: A firewall change that cut off access

  • OPNsense
  • GNS3

The situation. After a change meant to open access to a server, nothing outside its network could reach it.

My method. Review the rules on each interface in order and by direction, find the rule that does the opposite of what was intended, correct only that rule, apply the change, and test from a different network.

Ticket 6: Finding unauthorized services

  • netcat
  • Ubuntu

The situation. A security lead needed to know which open ports on a server fell outside the permitted set.

My method. Scan the server's ports with whatever tool is available, compare the results with the permitted list, record the difference in the requested file, and report the full results.

What I learned

  • The first guess is often wrong. On one ticket I suspected the server, and the real cause was two routers away.
  • A loop looks different from a dead end. "Time to live exceeded" replies point to a routing loop, while silence points to a host or service that is down.
  • Respecting a user's "no" made me a better troubleshooter. It forced me to collect evidence on the network side first.
  • Document as you go. Clear notes made the final write up fast and accurate.
